# CodeAnt security pipeline example

Scan a full repository before staging, preserve findings, and evaluate secrets,
SAST, and SCA in separate jobs. This demo repository intentionally contains
vulnerabilities. The workflow never runs the vulnerable application or deploys it.

## Files to copy

- `.github/workflows/codeant-security.yml`: reusable workflow, one scan followed
  by three policy jobs and a staging placeholder.
- `.github/workflows/codeant-security-demo.yml`: caller; change the branch trigger
  and replace the legacy secret fallback with `secrets.CODEANT_TOKEN`.
- `examples/security-pipeline/report.py` and `policy.json`: report exporter and
  explicit example policy. Keep them at these paths in the calling repository.

Create a CodeAnt API token for your organization with the **Codeant CI/CD** role
and repository scope. Store it as the calling repository's Actions secret
`CODEANT_TOKEN`. Enable secrets, SAST and SCA analysis in CodeAnt. This existing
test repo can also use its previously configured `ACCESS_TOKEN_GITHUB` secret.

Use `mode: warn` for an initial review period and `mode: enforce` to block on
violations. Missing/incomplete results and infrastructure errors fail in both
modes. The workflow does not use `continue-on-error` to hide scan errors.

The example policy blocks any secrets and any HIGH/CRITICAL SAST or SCA findings.
Unknown SAST/SCA severities also block. Edit `policy.json` to change the severity
selection or maximum allowed finding counts. This policy is workflow code, not
an undocumented input to the CodeAnt action. The native CodeAnt verdict is kept
in `results.json` and labeled separately in the PDF.

## Reports and logs

Download `codeant-security-<run-id>-<attempt>` from the run's Artifacts section:

- `results.json`, `codeant.sarif`, `codeant-qg.xml`: returned by CodeAnt.
- `codeant-findings.csv`, `codeant-summary.pdf`: generated by this example.
- `codeant-run.json`: scanned repository, commit, and Actions run URL.

Reports upload before the scanner policy jobs, including when those jobs fail.
Keep the report files and GitHub's downloaded log archive for troubleshooting;
do not upload runner environment dumps, credentials, or the whole checkout.

The action downloads its script, sends repository/commit/filter metadata and the
token to CodeAnt, then polls for results. Source analysis happens server-side;
the runner does not upload a source archive or local container image. `scanners`
selects returned result engines; repository settings control executed analyses.

## Prevent deployment or merging

Replace the `Staging readiness` echo step with your deployment and retain
`needs: [scan, gates]`. A deployment in the caller workflow needs `needs: security`.
Require the resulting security checks in your branch protection/ruleset to block
merges. The caller skips fork PRs because GitHub does not provide repository
secrets to them. No branch protection or real deployment is changed by this demo.

To share the workflow across repositories, move the helper and policy to a trusted
central repository and explicitly check them out at a pinned revision. A reusable
workflow alone does not copy these files to application repositories.

## Validate the helper

```sh
python3 -m unittest discover -s examples/security-pipeline -p 'test_*.py'
```

Tests cover clean enforcement, warning versus enforcement, incomplete results,
scanner isolation, secrets, unknown severities, and CSV formula escaping.

## Current boundaries

The published `CodeAnt-AI/codeant-ci-scan-action@v0.0.5` has no `quality_gate`
input. This example applies its own explicit policies after collecting reports.
Native gate conditions can be enforced separately, but a native PASSED verdict
with no enabled conditions is not proof of an effective policy.

The CodeAnt registry scanner pulls images already in a registry. This example
cannot scan a local Docker image before its first ECR push, and does not claim
to demonstrate that capability.

ReportLab 4.5.1 is installed only to produce the example PDF. Gate evaluation uses
Python's standard library. No third-party report dependency is needed for gates.

## Real run evidence

Both runs scanned the public repository and returned 48 findings: 1 secret,
9 SAST findings (8 HIGH/CRITICAL), and 38 SCA findings (16 HIGH/CRITICAL).

| Mode | Run | Outcome |
| --- | --- | --- |
| Warning | [42304719043](https://github.com/codeanttesting/codeant-demo/actions/runs/42304719043) | All policy jobs recorded warnings; staging readiness ran. |
| Enforcement | [42305066053](https://github.com/codeanttesting/codeant-demo/actions/runs/42305066053) | All three policy jobs failed; staging readiness was skipped. |

The original report files and selected runner output are preserved under
[`evidence/warn`](evidence/warn) and [`evidence/enforce`](evidence/enforce), so the
examples remain available after Actions artifacts expire. These are historical
outputs for the commits identified in `codeant-run.json`, not a claim about every
future scan. Credential/setup log lines are omitted from the saved excerpts.

In these runs, the native verdict was PASSED with no native gate conditions
enabled. The explicit example policy still blocked enforcement, which illustrates
why a native verdict must be interpreted alongside its evaluated conditions.
